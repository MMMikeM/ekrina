import { bench } from "../../../bench.ts";

Create the searcher once per list and call it on every keystroke:

```ts
const search = createSearcher(products, (product) => product.title);

input.addEventListener("input", () =>
	render(search(input.value, { limit: 10 })),
);
```

Creating it reads nothing, so over 100,000 items it takes about {bench.at100k.createMs} ms.
Each item is prepared the first time a query matches it, so the work spreads over the first few keystrokes and is never repeated.
When the list changes, create a new searcher; it takes as little time as the first one.

## Pass `limit`

When only the top of the list is shown, pass `limit` rather than slicing:

```ts
search("ma", { limit: 10 }); // the same ten results as search("ma").slice(0, 10)
```

Once `limit` items match the query as typed, the fuzzy and corrected matches that could not outrank them are never computed.
That matters most for one- and two-character queries over a large list.

## Which keystrokes rescan

A keystroke that extends the last query rescans only the items the last one matched, so a word gets faster as it is typed.
A few keystrokes rescan the whole list instead:

- starting a second word;
- five or more characters that fewer than ten items match as typed, since they might be a typo;
- four characters that nothing matches.

The first of those also builds the searcher's index over the whole list, once.

## Build the index ahead of time

To build the index before anyone types, once the list has loaded or while the page is idle, call `buildIndex()`:

```ts
const search = createSearcher(products, (product) => product.title);
requestIdleCallback(() => search.buildIndex());
```

Over 100,000 items it takes {bench.at100k.buildIndexMs} ms, and a session of 24 queries then takes {bench.at100k.sessionIndexedMs} ms instead of {bench.at100k.sessionMs}.
Results are identical either way.
A searcher that answers one query and is thrown away gains nothing from `buildIndex()`: over 10,000 items it comes out level or a little slower, and over 100,000 building the index makes that one search take a fifth to a quarter longer, so leave that one lazy.

## Text in other scripts

Results are the same in any script, but the index can't tell non-Latin letters apart.
On Greek, Cyrillic or CJK text it lets every item through, so each query scans the whole list, which is slower over a large list.
